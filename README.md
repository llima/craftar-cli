# Craftar

Craft, sync and convert AI-coding workspace harnesses — rules, agents, commands, skills, MCP servers — across every client workspace you maintain and every AI coder each team uses.

> Status: **phase 1 in progress** — phase 0, the foundations, is done. `import`, `sync`, `status`, `diff`, `explain`, `ls` work end-to-end for the `claude-code` and `kiro` targets and are validated byte-for-byte against a real workspace (see *Oracle*). The Forge commands `forge variants`, `forge diff` (with a suggested class per hunk) and `forge unify` (`--take base|variant`, `take: param` to turn a value into a `{{key}}` parameter, and `take: section` to turn a client block into a section) and `forge promote` (a profile's variant becomes the base) also work, covered by the unit and golden suites rather than the oracle, and `import` is render-aware: importing into an existing Forge reuses a base whose render equals the workspace file, and edits an existing profile and the recipes it owns in place. Ingredient bodies can hold client-specific **sections** (`<!-- craftar:section <name> -->` … `<!-- /craftar:section -->`), overridden by a profile's `sections` and a workspace's `overrides.sections`; import infers each client's content and `forge unify` can extract a section from a variant, and a Forge that uses them declares `schema: 2` or above (see *Forge layout*). The read-only catalogue — `recipes`, `ingredients` and `targets` with the capability matrix — works too, and a workspace can name its Forge by git URL with an optional `ref`, read from a per-machine cache, with a lock that records the ref, commit, recipes and targets it was generated from (see *Remote Forge*). `add recipe` / `remove recipe` change a workspace's recipe choice in `craftar.yaml`, refusing an edit that would not resolve. A writing `sync` records each workspace in a per-machine registry, and `craftar workspaces` lists them all with their status (see *Workspace registry*). `craftar forge impact` lists the workspaces registered on this machine that read a Forge (by path, by a git remote of the clone, or through another clone of the same remote) with what their next sync would do against it, and `forge unify` plans them before and after its writes, names the ones its warnings concern, and with `--prune-recipes` deletes a recipe left identical to its sibling once every one of them plans the same. `craftar doctor` reports, one line per finding, what is off on this machine and in this workspace. `craftar cache prune` removes the cache entries and trees nothing uses. An MCP ingredient can declare `authEnv`, the environment variables its server needs (names only, never a value), and `craftar doctor` checks them; with `claude-code`, `sync` writes an example file listing them. A recipe can bring **local services**: a `service` ingredient is a Docker Compose fragment that `sync` writes under `.craftar/`, and `craftar services up | down | status` run Compose on what the lock records (see *Local services*). A profile's `integrations` block can select recipes and give params in a Forge that declares `schema: 3` or above (see *Integrations*), since `0.27.0`. `craftar templates list | install` shows and runs the profile's `templates` block — `install` runs `dotnet new install` per entry into the user's template store; nothing installs implicitly. An MCP `server` takes the params its ingredient declares, in a Forge that declares `schema: 4` (see *Server params*), since `0.28.0`. `craftar mcp` serves a workspace to an AI coder over the Model Context Protocol — seven reading tools with the data of `status`, `diff`, `explain`, `recipes`, `ingredients`, `targets` and `doctor`; started with `--allow-writes`, it also serves `sync`, `add_recipe` and `remove_recipe`, which write only in a workspace where a person typed `craftar mcp allow-writes` and never discard a hand edit. `craftar ui` serves a local, read-only dashboard of every registered workspace — the table of `craftar workspaces`, and for one workspace its file states, a file's diff and explanation, and its Forge's recipes and ingredients — on `127.0.0.1` only; started with `--allow-writes`, it also syncs a workspace or discards one hand-edited file, each confirmed in the page and never with `--overwrite-drift`. `craftar init --clone` and `craftar repos clone` clone a profile's repositories (its `repos` list) into the workspace, and `craftar repos` lists them. `craftar init --new-profile` creates a profile in a Forge directory (one file, not committed) and starts the workspace on it. With `agents-md.primary`, in a Forge that declares `schema: 5`, an always-on rule lives in `AGENTS.md` alone, and the files that cite it follow it (see *Targets*). A `hook` ingredient can declare its `registration` — the event, matcher and command Claude Code runs it with — and `claude-code` writes it to `.claude/settings.craftar.example.json`, to copy into `.claude/settings.json`; `craftar doctor`'s `hooks-registered` says when a planned handler is in no settings file Claude Code reads (see *Hook registration*). In a Forge that declares `schema: 6`, a section can name the targets that receive it (`targets=`, see *Forge layout*). In a Forge that declares `schema: 7`, `{{craftar.rules.index}}` alone on a line of a rule or steering body becomes the list of the profile's rules (see *Forge layout*). A Claude Code plugin in this repository holds a `/craftar` skill and starts the `craftar` you installed, as `craftar mcp` with its reading tools only (see *Craftar inside the AI coder*). A symbolic link does not carry craftar out of the tree it works on: a Forge file read through a link that leaves the Forge, and a workspace path that leaves through one, are refused, with no flag.

## The idea in one paragraph

You write the harness **once**, in a central repository called the **Forge**, as small reusable **ingredients** (a rule, an agent, a command, a skill, an MCP server). **Recipes** bundle ingredients (`base`, `stack-backend-api`, `stack-frontend-angular`…). A **profile** describes a client: which recipes, which targets (Claude Code, Kiro, AGENTS.md…), and the parameters that differ per client. A workspace holds a tiny `craftar.yaml` pointing at the Forge and a profile; `craftar sync` generates `.claude/`, `.kiro/`, `AGENTS.md`… from it and records what it wrote in `craftar.lock`. Generated files are never edited by hand again — you edit the Forge and sync everywhere.

## Quick start: start an empty workspace from a Forge

```bash
# In a terminal, craftar init asks for what the flags do not give:
# the Forge, the profile, then the recipes and the targets to keep or adjust.
cd C:/Projects/acme-portal-workspace
craftar init

# Or pass everything for scripts and CI:
craftar init --workspace C:/Projects/acme-portal-workspace \
  --forge   C:/Projects/forge \
  --profile acme-portal
```

The workspace follows the profile's recipes and targets; `--add-recipe` / `--remove-recipe` adjust the recipes, and `--targets` writes the targets into `craftar.yaml`. When the directory already holds a harness, files equal to the Forge's are adopted and different ones are left as they are and reported — `craftar import` (below) brings them into the Forge.

A new client's first workspace starts its profile too:

```bash
# Creates profiles/initech/profile.yaml in the Forge directory (not committed), then the workspace on it
craftar init --workspace C:/Projects/initech-portal-workspace \
  --forge       C:/Projects/forge \
  --new-profile initech --like acme-portal
```

## Quick start: bring an existing workspace into a Forge

```bash
# 1. Import the harness of a Claude Code workspace into a (new or existing) Forge
craftar import --from claude-code \
  --workspace C:/Projects/acme-portal-workspace \
  --forge     C:/Projects/forge \
  --profile   acme-portal \
  --write-config          # writes craftar.yaml into the workspace

# 2. See what sync would do. On a freshly imported workspace everything is "adopt":
#    the files already on disk are exactly what the Forge produces, so they just become managed.
#    (A JSON file that differs only in whitespace is also "adopt"; the first sync rewrites it.)
craftar status --workspace C:/Projects/acme-portal-workspace

# 3. Generate + lock
craftar sync --workspace C:/Projects/acme-portal-workspace
```

From then on, change a rule in `forge/ingredients/rules/<name>/rule.md`, run `craftar sync` in each workspace (or `craftar sync --check` in CI) and every target is regenerated.

## Commands

| Command | What it does |
|---|---|
| `craftar init [--forge <dir\|url>] [--profile <name>] [--new-profile <name> [--like <profile>]] [--ref <ref>] [--targets <a,b>] [--add-recipe <name>]... [--remove-recipe <name>]... [--replace] [--no-sync] [--clone \| --no-clone] [--offline] [--workspace .]` | Starts a workspace: writes a `craftar.yaml` holding `forge` (a directory as the path from the workspace, POSIX; a URL as given), `ref` (a remote Forge only), `profile`, `recipes` (only the lists the recipe flags leave non-empty) and `targets` (only with `--targets`; otherwise the workspace follows the profile's), then runs the first `sync` — which also registers the workspace. **In a terminal** (stdin and stdout both a TTY), `--forge` and `--profile` are optional: what is missing is asked for — the Forge (offering the one last synced on this machine, from the registry), a remote Forge's ref, the profile (from the Forge's list), then the recipes and the targets the profile gives, to keep or adjust; a flag given is never asked for. One confirmation before anything is written, showing what the first sync would do. Ctrl-C, the end of input, or `no` at the confirmation: nothing written, exit 1 (`init cancelled — nothing written`). The run ends with an `again craftar init …` line: the same run as flags, for CI. Off a terminal (a pipe, CI), a missing flag is refused, exit 1, naming the flag; where the terminal does not report a TTY, the flags are required. With both flags given nothing is asked, in a terminal or not. The file is written only once the configuration loads (a remote Forge is fetched as `sync` fetches it; `--offline` reads the cache), resolves and plans, and the sync applies that same plan. `--remove-recipe` and `--add-recipe` go through `remove recipe` / `add recipe`'s core (removes first, then adds; `--replace` swaps a slot holder); a call whose every name changes nothing prints its reasons as a `note`. `--workspace` is created when missing. Files already on disk and not in a lock are adopted when equal to the plan and skipped as a `collision` otherwise, never overwritten, with one warning pointing at `craftar import`. `--no-sync` writes `craftar.yaml` only and prints what the first `sync` would do. When a declared parameter a file cites has no value (see `sync`), `craftar.yaml` is still written — the workspace's `overrides.params` is a place for the value — but the first `sync` is not run: the refusal is printed (`error: N declared parameter(s) have no value — craftar.yaml written, sync not run`, with `then run craftar sync` in its fix line), exit 1; in a terminal the confirmation says `first sync: refused — …` and asks only `Write craftar.yaml`; `--no-sync` prints `next sync: refused — …` and exits 0. Refused, with nothing written and no directory created: an existing `craftar.yaml`; a `--workspace` that is a file, or under one; credentials in `--forge` (the value is never printed); `--ref` with a directory Forge; an unknown target; a recipe both added and removed, or any refusal of `add recipe` / `remove recipe`; a `craftar.local.yaml` that sets `forge` or `profile`, or a key a given flag would write (`ref`, `recipes`, `targets`) — its value would replace the flag's; a Forge, profile or plan that does not load. **`--clone`** clones every entry of the profile's `repos` (see *Forge layout › Repositories*) into the workspace after the first `sync` — one `git clone --no-recurse-submodules [--branch=<ref>] -- <url> <path>` per entry, one after another, with the workspace root as working directory, `git` found in the absolute entries of `PATH` and `GIT_ALLOW_PROTOCOL=https:ssh`; git's own output and credential prompt go to the terminal, with no timeout. With `--no-sync`, `--clone` still clones. Without `--clone` nothing is cloned: with both `--forge` and `--profile` given nothing is asked and nothing is said about repositories; in a terminal, when a flag is missing, a profile with entries is listed — name, URL, destination, ref — and `Clone them into the workspace [no]:` is asked (Enter is no), except under `--offline` or `--no-clone`. A clone that fails is reported with the command to run it by hand and `craftar repos clone <names>`, the other entries are still tried, and `init` exits 1 with the workspace written, synced and registered. A first sync that would be refused clones nothing (`repositories: not cloned — the first sync is refused`). Refused before anything is written: `--clone` with `--no-clone`, or with `--offline`; `--clone` with no `git` on `PATH`, on a profile with no entry, with an entry that does not read, or with a destination that exists, holds a file `sync` writes, lies inside the Forge, leaves the workspace through a link or sits under a file. A clone is recorded nowhere — not in `craftar.lock`, not in the registry; `sync` never updates or removes it, and craftar does not edit a `.gitignore` (in a workspace that is itself a repository the clones show as untracked directories). **`--new-profile <name>`** creates the profile first: one new file, `profiles/<name>/profile.yaml`, in the Forge's working tree — its `name`, `recipes` and `targets` only — then starts the workspace on it as for a profile that was there. The Forge must be a directory that is a git repository with a commit (git is how the write is undone); nothing is committed, no branch is made and nothing is pushed — commit the file in the Forge, on a branch, before anyone else syncs. With `--new-profile`, `--add-recipe`, `--remove-recipe`, `--replace` and `--targets` shape **the profile**, and `craftar.yaml` gets no `recipes` and no `targets`. `--like <profile>` starts the new profile's `recipes` and `targets` from that profile's written lists — nothing else of it is copied: no `params`, `sections`, `integrations`, `repos`, `templates` or `description`; in a Forge at schema 3 or above a recipe only its `integrations` block selects does not come along, and a `note` line says so. The name is lowercase letters and digits in groups joined by one `-` (no `--`, not a Windows device name). Refused before anything is written: `--new-profile` with `--profile`, `--like` without `--new-profile`, a name of another shape, a Forge URL (clone it and pass the directory), a tree of craftar's Forge cache, a directory that is not a git repository with a commit, a name a profile already carries or a `profiles/<name>` that exists, a path git ignores or that goes through a symbolic link, a recipe named for another profile (`<recipe>--<p>`, `<p>-steering` — add the shared recipe it stands for), and a profile that does not resolve or plan. The Forge is planned in memory, the file written, then the Forge read back from disk must plan the same bytes before `craftar.yaml` is written; a failure after the profile was written exits 1 and prints the `git -C <forge> clean -fd -- profiles/<name>` line that removes it. In a terminal the profile list offers `0) a new profile` (for a Forge directory that can take one), and a Forge directory with no profile goes straight to the new profile's questions; the `again` line then names `--profile <name>`, the run a second workspace of that client uses. |
| `craftar repos [--workspace .] [--offline] [--json]` | Lists the profile's repositories (its `repos`, see *Forge layout › Repositories*) with their state in the workspace — `present` (the destination exists; craftar does not look inside), `missing`, or `blocked` with the reason a clone would be refused — and each one's destination, URL and ref. It loads the Forge as `status` does (a remote Forge is fetched unless `--offline`; a failed fetch is a warning over the cached copy), starts no other program, contacts no repository's host and writes nothing. A profile with no entry prints `profile <p> lists no repositories`. Exits 0 whenever the block reads, missing entries included; 1 for a block that does not read, or a workspace that does not load or plan, as `status`. `--json`, a tooling contract: `{workspace, profile, repos: [{name, url, path, ref, state, reason}], warnings}` (`ref` and `reason` `null` when absent). |
| `craftar repos clone [<name>…] [--workspace .]` | Clones the `missing` entries — every one, or the names given (compared without case) — as `init --clone` clones them; typing the command is the consent, and nothing is asked. A `present` entry is skipped with a line; a named one is refused. Refused before any clone, exit 1: no `git` on `PATH`; a remote Forge that cannot be fetched (it never clones from a cached copy, and has no `--offline`); a profile with no entry; a block that does not read; any `blocked` entry; a name that is not an entry, or is given twice. It clones whatever the workspace's sync state, and exits 1 when a clone fails, with the command to run it by hand. It writes the clones only: no `craftar.yaml`, lock or registry entry. |
| `craftar import --from claude-code --forge <dir> --profile <name> [--workspace .] [--write-config] [--report <file.md>] [--prefer-kiro <rule,…>]` | Reads `.claude/{rules,agents,commands,skills,scripts,hooks}`, `.mcp.json` and, when present, `.kiro/steering` (for inclusion modes and hand-written steering — and, with `--prefer-kiro`, the text of the rules it names). Scripts and hooks sharing the same base name (e.g., `run-x.ps1` and `run-x.sh`) become one ingredient listing all those files; two that differ only in case are rejected (the rest of the import proceeds). A rule's scope comes, in this order, from: a hand-written `.kiro/steering/<name>.md` whose frontmatter sets `inclusion`; a usable `paths:` in the rule's own frontmatter — a non-empty one-line string or a list of them, quoted or not (`- **/*.ts` is read as Claude Code reads it) — which gives `inclusion: fileMatch` and `fileMatchPattern`; a steering mirror craftar generated (its default banner); any other steering file, as before; and `always`. When `paths:` is usable the rule's frontmatter is kept verbatim apart from its body (`frontmatterRaw`), whichever source set the scope, so `.claude/rules/<name>.md` is written back byte for byte and neither `.kiro/steering/<name>.md` nor `AGENTS.md` carries it — except a file whose closing `---` is not followed by a newline, which keeps its frontmatter in its body and is written back as is; its steering mirror — and `AGENTS.md`, where it embeds the rule — then carry the block. What the workspace sees next, for a rule a craftar before this one read as always-on: its `.kiro/steering/<name>.md`, `AGENTS.md` and the `.kiro/agents/*.json` of agents bound to the rule now differ from the plan — where `craftar.lock` records them unedited, `sync` updates them; with no lock entry for them (a first import), they read `collision` and are left alone: delete them and run `craftar sync`. Four warnings name the rule and its files, never the pattern: the hand-written steering file and `paths:` disagree (the steering file's scope is kept); the generated mirror disagrees with `paths:` (scope taken from `paths:`); the steering file sets no `inclusion` (scope taken from `paths:`); `paths:` is not a string or a list of strings (ignored). With `--prefer-kiro`, a steering body that starts with a frontmatter block (as an earlier craftar wrote a `paths:` rule) is taken with it, as before, and the rule keeps no separate frontmatter. Creates ingredients, recipes (`base`, one `stack-*` per scoped rule, `<profile>-steering`) and a profile, or updates them. An ingredient already in the Forge is reused when the base, **rendered** for this profile (its declared defaults, the profile's `params`, the workspace's `overrides.params`), equals the workspace file; failing that, when a unique, proved assignment of the base's declared `{{keys}}` reproduces it, the values are **inferred** into the profile's `params` (one value per key per run; never a change another ingredient would feel). A base with section markers is rendered with the profile's `sections` and the workspace's `overrides.sections` first; when the workspace file differs from it only inside sections, the unique content that reproduces the file byte for byte is **inferred** into the profile's `sections` (tried after params, never combined with them; the report counts lines and never prints the content). An import that writes a section value, or compares a workspace file against a base holding markers, sets `schema: 2` in `craftar.forge.yaml` (a manifest already at 2 or above is left as it is). A reused base takes the place its `<name>--<profile>` variant held: the profile moves to the shared recipe when that orders the base there, and an owned recipe gets the base in the variant's slot, so the rule order (and `AGENTS.md`) stays as it was. Anything else becomes a `<name>--<profile>` variant that emits under the original name, with the reason, so the workspace still round-trips while you decide what to unify. A shared recipe is never widened for one client: a profile whose ingredients differ from `base` or a `stack-*` gets its own `<recipe>--<profile>`. An existing profile is merged in place (`params`, `sections`, the recipes import owns, missing `targets`; every other field and comment kept, and an empty `{}` / `[]` it does not change stays on its line), as is a recipe the profile owns; `--write-config` merges an existing `craftar.yaml` (`forge`, `profile`, `targets`). The report adds `rendered` (with `sections <names>` when a section value filled the render), `inferred`, `sectioned`, `param <key>: <old> → <new>`, `section <key> <name>: <old> → <new>`, `forge craftar.forge.yaml edited (schema: 2)` and `profile … created\|edited\|unchanged` lines. In a Forge at schema 3 or above, what the profile's `integrations` block alone provides is **not imported** — not compared, not written — and is listed (`left to recipe <r> (integrations.<slot>): …`, and under `## Left to an integration recipe` in the `--report` file); `craftar status` then shows whether the workspace's copies differ (`drift`, `collision`); move an agent attached to a scoped rule into the integration recipe with its rule, or `base` splits on import. It refuses, with the Forge untouched, a `--forge` or `--report` inside craftar's Forge cache (a tree there, or a directory it would create there), a Forge that does not load, a profile or recipe or `craftar.yaml` that does not round-trip through the YAML writer, a misplaced profile, a recipe import writes whose file and `name` disagree, a workspace override that does not parse, a literal `{{key}}` the profile would render, changing a recipe or variant another profile uses, a workspace file holding a section marker at column 0 (sync would not reproduce it: indent it), a Forge base with malformed section markers, a `craftar.forge.yaml` it needs to bump to `schema: 2` that does not round-trip (set it by hand), and — in a Forge at schema 3 or above — a profile whose `integrations` block is malformed or, when the block holds a `kind`, that does not resolve. Ingredients holding a secret-like value (tokens, private keys, high-entropy MCP `env`/`args` values) are rejected and listed by location — the value is never printed. `authEnv` is never inferred; a variant import rewrites keeps the one it declares, a new variant takes its base's, and a declaration a profile loses is reported. A UTF-16 file with a byte-order mark is decoded for the scan; UTF-16 without one is not detected. An ingredient that would not load back into the Forge (a name that is not slug-like, a non-string MCP `env` value) refuses the import, naming its source; so does an ingredient already in the Forge whose `ingredient.yaml` has an unknown key or a YAML syntax error, naming that file. Every read and check runs before the first write, so an import that fails leaves the Forge untouched and says so. `--report <file.md>` also writes a Markdown report, after the Forge is written: what was created, reused, made a variant or rejected, the import's warnings, and the Kiro side — *Kiro collisions*, every `.kiro/` file that differs from what `sync` would generate for the imported profile (`status`' `collision` state against no lock, so a difference of line endings, BOM or JSON formatting is not one), each with its ingredient and the line counts of the two sides, a rule's steering mirror that outgrew its rule marked `steering bigger than the rule` (not one `--prefer-kiro` took the rule from); and *Unsourced Kiro files*, the files under `.kiro/steering/`, `.kiro/agents/`, `.kiro/skills/` and `.kiro/settings/mcp.json` that the plan for the imported profile does not write — listed, never imported. The report holds **paths and line counts, never content** (a `.kiro/` mirror is not scanned for secrets), and names an inferred parameter's key, not its value; a warning, a rejection reason or the `not computed` line is written with every parameter and section value this run accepted, replaced or inferred as `"…"`, and a variant is named against its base, without its reason — the summary on the terminal keeps them. It describes the profile as imported: of the workspace's own `craftar.yaml` and `craftar.local.yaml` only `overrides.params` and `overrides.sections` are read (as import reads them to decide a reuse) — not its `forge`, `profile`, `targets` or recipes — and `craftar.lock` is not read. The path may be inside the workspace; it is refused, before anything is imported, when it resolves inside the Forge (through symlinks and `..`), when a file already exists there, or when a component of it cannot be resolved. If the Kiro side cannot be computed — the plan fails, or `sync` would refuse it for a declared parameter with no value — its sections read `not computed: …`, the same is an import warning, and the import still exits 0. The report is written after the summary, which then ends with `report <file.md>`; if that write fails the import has still succeeded and the Forge is written, and the command says so and exits 1. Without `--report` none of this is computed. `--prefer-kiro <rule,…>` takes the named rules from `.kiro/steering/<name>.md` instead of `.claude/rules/<name>.md` — for a steering mirror that was edited by hand and is the text to keep; a rule left to an integration recipe is warned (`nothing to prefer; its steering file was not used`) and skipped, before that rule's own refusals (no steering file, a form with no certain source, a line that would not come back). The rule's text is built from the steering file — its frontmatter and its opening banner (the default one, or the line rendered by the `kiro.banner` sync would use: the workspace's `overrides.params`, else — for a profile already in the Forge — the profile's own or a default of a recipe it resolves) dropped, `.kiro/steering/` turned back into `.claude/rules/` except in a reference to a hand-written steering file and under `commands/` — and is accepted only when it is **proved to render back** to that steering file's body for Kiro over the workspace's own rules (every rule aimed at every target, as import writes them); it is then scanned for secrets and decided like any source (reused, a variant, or created; a rejection names the steering file's line, and a rejected rule gets no `prefer-kiro` line), its `inclusion` and `fileMatchPattern` still read from the steering frontmatter. Refused, with the Forge untouched: an empty or repeated name; a name with no `.claude/rules/<name>.md` (the flag takes rules; a steering file with no rule is already imported as steering); a rule with no `.kiro/steering/<name>.md`; a steering file holding a form Kiro writes for a rule it does not have (`AGENTS.md (rule: <x>)`, a link to `AGENTS.md`, `rule not in this workspace`), which has no certain source; a steering file that would not come back from the rule built from it (it names `.claude/rules/` where `sync` writes `.kiro/steering/`); and — in a Forge at schema 7 — a rule the profile resolves whose body holds `{{craftar.rules.index}}` (the steering text holds the generated list, which import would freeze) — the last three name the line of the steering file and quote none of it. The ingredient's `origin.path` is the steering file; the summary gains `prefer-kiro <ref> — source .kiro/steering/<name>.md (N lines; .claude/rules/<name>.md has M)` per rule — N and M count the two files whole, the steering file's frontmatter and banner included — and `--report` a *Preferred from Kiro* section with the same lines. What the workspace sees next: the Forge rule now differs from `.claude/rules/<name>.md` on disk, so with no lock entry for that file the next `sync` shows it as `collision` and leaves it alone — delete it (and the steering file, if it also collides) and run `craftar sync` to regenerate both; where `craftar.lock` already records the file unedited, `sync` updates it. The summary says so in a `note` for each rule whose text changed (after the warnings, before the `report` line). ## Forge layout

```
forge/
├── craftar.forge.yaml
├── ingredients/
│   ├── rules/<name>/{ingredient.yaml, rule.md}
│   ├── agents/<name>/{ingredient.yaml, agent.md}
│   ├── commands/<name>/{ingredient.yaml, command.md}
│   ├── skills/<name>/{ingredient.yaml, SKILL.md, …}
│   ├── scripts/<name>/{ingredient.yaml, <file>…}
│   ├── hooks/<name>/{ingredient.yaml, <file>…}
│   ├── mcp/<name>/ingredient.yaml           # server definition (its declared params rendered at schema 4)
│   ├── steerings/<name>/{ingredient.yaml, steering.md}   # Kiro-only, no Claude counterpart
│   └── services/<name>/{ingredient.yaml, compose.yaml, …}   # a Compose fragment and its files — no AI coder's; see Local services
├── recipes/<name>.yaml
└── profiles/<name>/profile.yaml
```

An ingredient's `as` and a script's or hook's `files` entries become part of the paths `sync` writes, so one that climbs out of its folder with `..` (`as: ../x`, `files: [../x.sh]`) fails the Forge load. A leading `/` anchors nothing (`/../x` is refused too). A spelling that stays inside (`./run.sh`, `a/../run.sh`) is kept as written.

`craftar.forge.yaml`:

```yaml
name: forge
schema: 2          # 1 (the default), 2, 3, 4, 5, 6 or 7; 2 is required for section markers, 3 for integrations, 4 for params in an MCP server, 5 for agents-md.primary, 6 for target-scoped sections, 7 for the rules index — each includes the ones below it
description: Craftar Forge — shared harness ingredients, recipes and client profiles.
```

`ingredient.yaml` (rule):

```yaml
type: rule
name: frontend-angular
inclusion: fileMatch                 # always | fileMatch | manual | auto  (Kiro steering modes)
fileMatchPattern: projects/acme-portal-front/**
targets: "*"                         # or [claude-code, kiro]
tags: []
origin: { workspace: acme-portal-workspace, path: .claude/rules/frontend-angular.md }
params:                              # optional: {{deploy.api}} in the body renders "acme-portal-api" unless a stronger layer sets it
  deploy.api: { default: acme-portal-api, description: The API repository }
```

The keys above are the whole vocabulary (`params` declares the ingredient's own parameters: each `default` is a string, number or boolean, and fills only this ingredient's placeholders): an `ingredient.yaml` with a key the schema does not declare (a typo such as `incluson`, or a field no command reads) fails to load, and the error names the file and every unknown key at once. The one exception is an MCP server, which is the tool's own configuration: `command`, `args`, `url`, `env` and `type` are checked, and every other key is kept and emitted as it is, in the order the Forge holds it.

`ingredient.yaml` (mcp):

```yaml
type: mcp
name: acme-docs
authEnv: [ACME_DOCS_TOKEN]           # names only, never a value
targets: "*"
tags: []
server:
  type: http
  url: https://mcp.acme.dev/docs
  headers: { X-Team: acme }          # not declared by Craftar: passed through to both MCP files
  timeout: 30
```

`authEnv` names the environment variables the server needs — names only, never a value. It is a declaration: below `schema: 4` the server is emitted exactly as written, and at 4 only the params it declares are rendered into it — see *Server params* (how the server receives the variable is yours to write: a `${NAME}` reference where the tool expands one, or nothing at all for a server that inherits the environment — Craftar never expands it). An item that is a token of a known format fails the load.

**Server params.** In a Forge that declares `schema: 4`, an MCP ingredient can hold one server for every client and take the part that differs from a param it declares:

```yaml
# ingredients/mcp/idp/ingredient.yaml          # profiles/acme/profile.yaml
type: mcp                                       recipes: [base]        # base lists mcp/idp
name: idp                                       integrations:
params:                                           idp:
  integrations.idp.url: {}                          url: https://idp.example.com/mcp
server:
  type: http
  url: "{{integrations.idp.url}}"
```

(The block has no `kind` here, so it only gives the param. With `kind: generic` the Forge would also need a recipe `idp-generic`.) At schema 4 every **string value** of `server` — `url`, `command`, each item of `args`, each value of `env` and `headers`, any key the tool defines, at any depth — has `{{key}}` replaced **for the keys the ingredient declares in its own `params`**, with the value the layers give (the ingredient's default, recipe defaults, the profile's `integrations` and `params`, the workspace's `overrides.params`). Never a key (a server name, a variable name, a header name), never a number or a boolean; the result is always a string (`port: "{{port}}"` renders `"8080"`), and substituted text is not substituted again. `${NAME}` and a tool's own `{{ … }}` are left alone. Both `.mcp.json` and `.kiro/settings/mcp.json` get the same rendered server. Below `schema: 4` a server is written exactly as the Forge holds it, braces included, with no warning. Schema 4 includes 3 and 2: a Forge that moves from 2 to 4 also gets its `integrations` blocks read.

What `sync` does with a `{{key}}` in a server, at schema 4:

| The key is | Result |
|---|---|
| declared by the ingredient, and some layer gives it a value | substituted |
| declared, with no value in any layer | left as written, and **the sync is refused** — a server is a file `sync` writes, so this is the unset declared-parameter refusal (`sync`, `sync --check`, `status`, `diff --exit-code` exit 1) |
| not declared by the ingredient, while some layer gives the key a value | left as written, with one warning per ingredient and key: `mcp/idp: server cites {{org}}, which has a value but is not declared in the ingredient's params — left verbatim` |
| not declared, and no layer gives it a value | left as written, silently: braces that belong to the tool |

**The credential check.** `.mcp.json` is generated and committed, and a param's value can come from any hand-written layer — the gitignored `craftar.local.yaml` among them. This is not the check on a `forge:` URL (see *Remote Forge*): the two read a URL by different rules. So at schema 4 every **substituted** value of every server a target writes is checked before a plan is returned:

- a URL with credentials (`url-credentials`), as the whole value or inside it, or a token of a known format (its kind, such as `github-token`) **fails the plan**: `sync` (also `--check` and `--dry-run`), `status`, `diff`, `ls` and `explain` exit 1 and write nothing, the `drift` commands fail the same way, `add recipe`, `remove recipe` and `init` refuse before they write, `doctor` reports it under `plan`, `craftar workspaces` and `forge impact` show `error`;
- a high-entropy value under `env` or `args` (`high-entropy-value`) **warns**, and the plan stands — organisation and project names in `args` can look like one. (A warning fails `doctor --strict`.)

The message names the ingredient, the field and the kind — `mcp/idp: the value rendered into server.headers.Authorization looks like a credential (github-token) — …` — and never the value. The way out is to keep the secret out of a param: have the server read it from the environment, and declare the variable in `authEnv` so `doctor` and the example settings file name it. A URL whose userinfo is made only of `${NAME}` references, such as `https://${IDP_USER}:${IDP_TOKEN}@idp.example.com/`, is let through. `doctor`'s `mcp-env` checks the names it finds in the rendered server's `env` and in `authEnv`; it reads no other field.

The check narrows the road; it does not close it. **Still passes, though it is a secret:** a token of an unknown format (outside `env` and `args` nothing looks for it; inside them it can only warn, and only when the whole value is letters, digits and `+ / = _ -`) — so `Bearer <token>`, `KEY: <token>` and a `…;Password=…` connection string pass when the token's format is not a known one; a secret in a URL's path or query (`https://idp.example.com/mcp?api_key=<token>`); a URL userinfo holding `/`, `?`, `#`, a quote, `,` or `;`, or white space other than a tab or a line break directly before the `@` — so a token followed by a space (`https://<token> @host/`) passes, and so does a tab inside the userinfo; a quote, `,` or `;` directly after the `://`; a user-only token whose scheme is broken by a space (`ht<SPACE>tps://<token>@host/` — it no longer reads as `http(s)`; with a password it is still refused; a tab or a line break inside the scheme or its `://` is read past since 0.32.1); credentials with no `://` (`user:<secret>@host`); a user-only token on a scheme that is not `http(s)`, `ws(s)` or `<x>+` one of them (`ssh://<token>@host/`); anything that is neither a URL with a userinfo nor a token of a known format. One more way a value can show: a param value written as `${<something>}` and rendered under `env` reads, to `doctor`'s `mcp-env`, as a variable reference: it prints `<something>` as the name of a variable it expects when that has the shape of a name and is not set — a known token format inside the braces is refused before that, an unknown one is not. **Refused, though it is not a secret:** a URL on `http(s)`, `ws(s)` or `<x>+` one of them with a user and no password (`https://acme@dev.azure.com/acme/Portal`); a userinfo that is not made only of plain references — a literal mixed with one (`postgres://acme:${DB_PASS}@db.example.com/app`; write `${DB_USER}:${DB_PASS}`) or a reference with a default (`https://${A:-x}@host/`); a URL with no path followed, with none of `/ ? #`, white space, a quote, `,` or `;` between, by text holding an `@` (`https://a.example.com&cc=ops@example.com`); a URL on any scheme but `file` written with an empty authority — extra `/`, `\` or white space after the `://` — when what follows then reads as a userinfo (`sqlite:///a:b@c.db`; on `http(s)`, `ws(s)` or `<x>+` one of them an `@` alone is enough: `https:///ops@example.com`; in prose, `see :// a:b@c`); a URL with no path, query or fragment followed by a tab or by line breaks — a blank line between too — and then an `@` (`https://registry.npmjs.org`, then `@acme/pkg` on the next line; a markdown link or an unquoted CSS `url(…)` followed by a line that starts with `@`), since a tab, a line feed or a carriage return directly before an `@` is read past — on a scheme that is not `http(s)`, `ws(s)` or `<x>+` one of them, only when the text before the `@` holds a `:`, such as a port; a standalone run of 52 lowercase letters and digits that holds a digit. The only way round a refusal is to keep the value out of a param: write it literally in the ingredient, or have the server read the environment. A literal the Forge author wrote in a server, with no placeholder in it, is **not** checked, at any schema: it is emitted as written, and `craftar import`'s scan stays the guard on what enters a Forge.

**Hook registration.** A hook ingredient writes its files under `.claude/hooks/` and nothing else. What makes Claude Code run one — an entry under `hooks.<Event>[]` with a `matcher` and a `command` — is written by hand, into a settings file. A hook's `ingredient.yaml` can declare a `registration` to have `sync` write that entry into `.claude/settings.craftar.example.json`, beside `env`:

```yaml
# ingredients/hooks/guard-path/ingredient.yaml
type: hook
name: guard-path
files: [guard-path.py]
params:
  hooks.python:
    default: python3        # Linux and macOS; Windows overrides it below
registration:
  - event: PreToolUse
    matcher: "Bash|PowerShell"
    command: "{{hooks.python}}"
    args: ["${CLAUDE_PROJECT_DIR}/.claude/hooks/guard-path.py"]
    timeout: 10
```

On a Windows machine, in `craftar.local.yaml` (personal, gitignored):

```yaml
overrides:
  params:
    hooks.python: python      # python.exe on Windows
```

The user copies the `hooks` block into `.claude/settings.json` or `~/.claude/settings.json` once; `sync`, `diff` and `doctor` tell them when it changes.

| Field | Required | Shape | Written as |
|---|---|---|---|
| `event` | yes | `^[A-Z][A-Za-z]*$`, at most 64 characters | the key under `hooks` |
| `matcher` | no | a non-empty string, at most 512 characters | the group's `matcher`; omitted when absent |
| `command` | yes | a non-empty string, at most 1024 characters | the handler's `command` |
| `args` | no | a list of strings, at most 64, each at most 1024 characters | the handler's `args` — exec form |
| `timeout` | no | an integer from 1 to 3600 | the handler's `timeout` (seconds) |
| `shell` | no | `bash` or `powershell`; refused with `args` | the handler's `shell` — shell form |

A `{{key}}` in `command`, `args` or `matcher` is replaced **only for keys the hook ingredient declares in its own `params`**, as for an MCP server — a declared key with no value refuses the sync, an undeclared key a layer values warns, and `${…}` is left for Claude Code. A substituted value is checked for credentials and known token patterns. A literal token in a registration fails the Forge load.

**The example file in a repository.** A per-machine value (the interpreter) makes the file differ between machines. Two choices: keep it out of the repository (`.gitignore`, and list it under `mayBeIgnored` in `craftar.yaml`, or `sync` warns and `doctor --strict` exits 1), or give the param a shared default every machine keeps. craftar picks neither and writes no `.gitignore`.

**Sections.** A body (its **body files**: the `file` of a rule, agent, command or steering — `rule.md` etc. by default; `SKILL.md` of a file-layout skill; every `.md`, `.txt`, `.json`, `.yaml` or `.yml` file of a dir-layout skill; the text files listed in `files` of a script or hook — a body file stays inside the ingredient directory; one declared outside it, or behind a symlinked directory, or spelled differently from the file on disk (letter case, on a case-insensitive file system), fails `sync`, `status`, `diff`, `explain` and `ls`, naming it) can hold blocks a profile or a workspace replaces. A file no target emits (a `notes.md` beside `rule.md`) is ignored — for sections and for `{{param}}` citations alike; a file a target emits but does not render as text is copied (see below). A block sits between two marker lines, and its content is the default:

```markdown
Dispatch reviewers after every commit.

<!-- craftar:section flavors -->
| Repo | Reviewer |
|---|---|
| `acme-api` | backend-reviewer |
<!-- /craftar:section -->

Never edit what a reviewer reads.
```

A marker is a whole line starting at column 0, with single spaces (trailing spaces or tabs are tolerated). Sections do not nest, a name is declared once per ingredient, and a line that looks almost like a marker is an error. An indented marker is plain text — indent it to show the syntax in a rule. The parser is line-based and not Markdown-aware, so a column-0 marker inside a fenced block is still a marker. Markers are read only in body files; in a file a target emits but does not render as text (a skill's `.sh`, an image) they are copied as they are, with a warning; in a file no target emits they are ignored. Agent and command frontmatter lives in `ingredient.yaml` and is never expanded; a rule's or skill's frontmatter is part of its body file, so a column-0 marker there is read like any other. A Forge whose bodies hold a marker must declare `schema: 2` or higher in `craftar.forge.yaml` (`3` includes it), so that craftar 0.6.2 and older refuse it instead of emitting the markers; `import` sets it to 2 when it relies on markers and the manifest is below 2. A section can also be extracted from a variant with `forge unify` (`take: section`), not only added by hand and re-imported.

**A section for some targets only.** In a Forge that declares `schema: 6` (which includes 5 and below), an opening marker can name the targets that receive the block: `<!-- craftar:section <name> targets=<target>[,<target>…] -->`, the targets among `claude-code`, `kiro` and `agents-md`, comma-separated with no space, each once. A target the marker names gets the section as any other — the workspace's value, else the profile's, else the default; a target it does not name gets nothing of it, whatever a profile or the workspace sets; a marker with no `targets=` is read as before, for every target. Where a section is left out, the texts around it join, and when the line before it and the line after it are both blank, one of the two blank lines goes with it. A `targets=` that is empty, names an unknown target, repeats one or ends with a comma fails the plan, naming the file, the line and the section, never the value; below `schema: 6` the attribute is not read and the line fails the plan as a near miss, saying the Forge must declare `schema: 6`. A `service` file is written for no target, so a section there with `targets=` fails the plan. A section that reaches no target writing its ingredient — `targets=kiro` in a rule whose `targets` is `[claude-code]`, or a section for `claude-code` in a rule `agents-md.primary` writes to `AGENTS.md` alone — is a warning. `import` and `drift promote` infer a value only for a section the source file's target receives (`claude-code` for `.claude/`, `kiro` for a rule taken with `--prefer-kiro`). A variant `import` or `drift promote` makes from one target's file holds that target's text only: a section for other targets is left out of it — `import` says which, `drift promote` lists every section of the base among those it flattened — and `import` also says when a section for that target, but not for all, is kept in it as plain text, which every other target the workspace writes it to then receives. `forge unify` refuses a merge that changes a section's targets, and the marker `take: section` writes never holds `targets=` — add it by hand.

Profile `profile.yaml`, with section values keyed by `<type>/<name>` (the output name: a variant's values are its base's), then by section name:

```yaml
name: globex
recipes: [base]
targets: [claude-code, kiro]
params: {}
sections:
  rule/review-posture:
    flavors: |
      | Repo | Reviewer |
      |---|---|
      | `globex-api` | backend-reviewer |
  rule/repo-discovery:
    desktop-client: ""               # empty: the section renders nothing for globex
```

A value is a string. It replaces the section's lines; a value without a final newline gets one, and `""` empties the section. The blank lines around the markers stay when a section is emptied, so put a separating blank line inside the section when an emptied section should leave none extra. A value may cite `{{param}}`: sections are expanded before params are substituted.

**The rules index placeholder.** In a Forge that declares `schema: 7` (which includes 6 and below), a line of a rule or steering body that holds `{{craftar.rules.index}}` alone is replaced by `sync` with the list of the rules the profile resolves, as each target names them (see *Targets*): up to three groups — `Always on:`, `Scoped:`, `On request:` — each present only when it holds a rule, one line per rule, `- <ref> — <description>`, a scoped rule adding `` (applies to `<glob>`) `` from its `fileMatchPattern`, and `- (no rules)` when nothing is listed. The description is the rule's `description`, folded to one line; a rule with none is listed by its reference alone and the plan warns once, `craftar.rules.index: no description for rule <a>, <b> — listed by name only`; a description holding `<!-- craftar:` fails the plan. The placeholder anywhere else — not alone on its line, or in an agent, a command or a skill — is left as written and warned. Below `schema: 7` it is left as written and warned too (`{{craftar.rules.index}} needs a Forge at schema: 7 — left as written in <ref> (<file>), …`), so `doctor --strict` exits 1 there. `craftar.rules.index` is generated, never a parameter: at `schema: 7` a value a recipe, the profile, the workspace or an ingredient gives it is ignored with a warning that does not print it, and a declaration of it never refuses a sync. Every key starting with `craftar.` is reserved, at every schema: `forge unify` never extracts into one and `import` never infers one.

**Repositories.** A profile's `repos` lists the client's repositories, for `craftar init --clone` and `craftar repos`:

```yaml
# profiles/acme/profile.yaml
repos:
  - name: portal-api
    url: https://git.example.com/acme/portal-api.git
  - name: portal-web
    url: git@git.example.com:acme/portal-web.git
    path: apps/portal-web            # optional, default: the name — relative to the workspace
    ref: release                     # optional: a branch or a tag
```

`name` is letters, digits, `.`, `_` and `-`, starting with a letter or a digit, not ending in `.`, not a Windows device name, and unique without case. `url` is an `https://`, `ssh://` or `user@host:path` URL made of `A-Z a-z 0-9 . _ ~ : / @ + -` only, its first character after `://` (or its first character, in the `user@host:path` form), its host and (in that form) its path each starting with a letter or a digit, and without credentials — let git authenticate. `path` is `/`-separated segments that each follow `name`'s rule (so no dot-folder), has a first segment that is none of `AGENTS.md`, `craftar.yaml`, `craftar.local.yaml` and `craftar.lock` (compared without case), and no two entries share or nest a destination (compared without case). `ref` is a branch or a tag, never a commit id. No other key. The block is checked only when a command reads it — a Forge whose `repos` holds something else still loads and syncs — and a refusal names the entry's index and key, never a value.

**Integrations.** A profile's `integrations` block can select recipes and give params in a Forge that declares `schema: 3` or above:

```yaml
# profiles/acme/profile.yaml — in a Forge whose craftar.forge.yaml declares schema: 3
name: acme
recipes: [base, stack-dotnet]
integrations:
  pm:
    kind: azure-devops
    org: acme
    project: Platform
  idp:
    kind: mcp
    url: https://idp.example.com/mcp
  browser:                # no kind: values only
    chromeDevtools: "1.7.0"
```

```yaml
# recipes/pm-azure-devops.yaml
name: pm-azure-devops
slot: pm
ingredients: [mcp/azure-devops, rule/stories-azure-devops]
```

```markdown
<!-- ingredients/rules/stories-azure-devops/rule.md -->
Stories live in Azure DevOps, organisation {{integrations.pm.org}}, project
{{integrations.pm.project}}.
```

`integrations.<slot>.kind: <kind>` selects the recipe **named** `<slot>-<kind>` — after the profile's own `recipes`, before the workspace's `recipes.add`; the mapping is by name, so a slot named like an unrelated recipe prefix selects that recipe (a slot `stack` with `kind: dotnet` selects `stack-dotnet`). Every scalar of the block, `kind` included, is the param `integrations.<slot>.<key>`, **under** the profile's own `params` (an explicit `params` entry of that key wins, silently) and under `overrides.params`; an integration with no `kind` gives params only; a mapping or a list is not a param and is warned wherever a resolution warning prints (`sync`, `status`, `recipes`, `doctor`, among others). **Only in a Forge that declares `schema: 3` or above** (what this README says of a schema 3 Forge holds at 4) — set by hand, never by a command; below 3 the block is ignored **without a warning**: if nothing happens, look at `craftar.forge.yaml`. A `kind` with no recipe, or a malformed block: `sync`, `status`, `diff`, `explain`, `ls` exit 1; `craftar recipes` marks nothing as in use and warns; `doctor` reports it under `plan`; `craftar workspaces` and `forge impact` show `error`; `craftar add recipe`, `craftar remove recipe` and `craftar init` fail (they resolve the profile); `import` into that profile and `drift promote` in any of its workspaces fail; a workspace whose `recipes.remove` names the missing recipe (written by hand: `craftar remove recipe` never adds a name the Forge does not have) resolves and syncs, but `import` and `drift promote` still refuse for that profile (they resolve the profile alone). Malformed: a slot name is letters, digits and `_`, starting with a letter; a key inside a slot is letters, digits and `_`; `kind` is lowercase letters, digits, `.`, `_`, `-`, starting with a letter or digit; a slot whose value is not a mapping — nothing under it (`pm:`), a string (`pm: azure-devops`), a list — is an error; a key with no value is absent. Another profile's malformed block does not fail `craftar recipes` or `forge unify --prune-recipes` run for this one — both read that profile's recipes as written and warn (`profile <q>: … — its recipes are read as written`). An integration param reads `(profile <name>)` in `craftar explain`'s `params` line. `import` never writes or edits a profile's `integrations`, and in a Forge at schema 3 or above never infers an `integrations.*` param. A workspace has no `integrations` of its own: `recipes.remove` takes the recipe out (the params stay), `overrides.params` changes a value; after `add recipe <other> --replace` on the same `slot:` the `{{integrations.<slot>.*}}` params still carry the block's values. Write the block in block style: a flow mapping with padding the YAML writer does not reproduce (`pm:  { kind: azure-devops }`, two spaces after the colon) resolves but `import`, `forge unify` (`take: param`, `take: section`, `--prune-recipes`) and `drift promote` cannot edit that profile file in place, as for any file that does not round-trip. A URL written in the block is rendered into a rule, a generated and committed file — as one written in `params` is; keep credentials out of both.

Recipe:

```yaml
name: stack-frontend-angular
extends: []
slot: frontend                       # optional: two recipes on one slot cannot coexist
ingredients: [rule/frontend-angular, agent/frontend-reviewer]
params: { angularVersion: { default: "20" } }
```

Workspace `craftar.yaml`:

```yaml
forge: ../forge # a path, or a git URL (see Remote Forge)
ref: v1.4.0 # optional, with a git URL: a branch, a tag or a full SHA
profile: acme-portal
targets: [claude-code, kiro] # optional, overrides the profile
mayBeIgnored: [.claude/settings.craftar.example.json] # optional: exact generated paths git may ignore here
recipes: {add: [], remove: []} # edited by craftar add recipe / remove recipe
overrides:
  params: {}
  sections: {} # same shape as the profile's sections
  ingredients: {disable: []}
```

Layer precedence, weakest → strongest: the ingredient's declared defaults (scoped to that ingredient) → recipe defaults → profile → `craftar.yaml` → `craftar.local.yaml` (personal, git-ignored). Bodies may use `{{param}}` placeholders; a placeholder in a file no target emits is never rendered, and only body files count as a citation for `forge unify` and `import` — plus, in a schema 4 Forge, the keys an MCP server cites **and its ingredient declares** (see *Server params*); a placeholder whose key some ingredient declares under `params` (with or without a default — a default reaches only its own ingredient's files) but has no value in any layer is left untouched, reported as a warning by `status` and `sync`, and refuses the sync when cited (see `sync` in *Commands*); a placeholder whose key is under `integrations.` in a Forge at schema 3 or above is warned the same way; any other `{{key}}` no ingredient declares is left verbatim **silently**. Between layers, objects merge key by key while arrays and scalars from the stronger layer replace the weaker one — `targets: [kiro]` in `craftar.local.yaml` means exactly `[kiro]`. Omit a key in `craftar.local.yaml` to inherit it — an empty list there means empty.

Sections layer the same way, weakest → strongest: the body's default → the profile's `sections` → `craftar.yaml`'s `overrides.sections` → `craftar.local.yaml`'s, merged per section, so a workspace that sets one section of an ingredient keeps the profile's others. There is no recipe layer for sections.

## Targets

`craftar targets` prints this matrix from `src/core/capabilities.ts`; a test plans one ingredient of every type for each target and fails when a cell and its emitter disagree. **native** — written in the tool's own place for that type, as the Forge holds it (for `mcp`, judged on the server file); **converted** — written in another form (frontmatter or a banner added, references rewritten, another container format, or folded into a shared file); **unsupported** — not written: `sync` warns and names an ingredient aimed at that target.

| type | `claude-code` | `kiro` | `agents-md` |
|---|---|---|---|
| `rule` | native | converted | converted |
| `agent` | native | converted | unsupported |
| `command` | native | converted | unsupported |
| `skill` | native | converted | unsupported |
| `mcp` | native | native | unsupported |
| `script` | native | unsupported | unsupported |
| `steering` | unsupported | native | unsupported |
| `hook` | native | unsupported | unsupported |
| `service` | unsupported | unsupported | unsupported |

**service** — unsupported in all three: a service is aimed at no AI coder (its `targets` defaults to `[]`, and an explicit one is skipped with the usual warning). `sync` writes it under `.craftar/` for no target — see *Local services*.

**claude-code** — emits `.claude/rules|agents|commands|skills|scripts|hooks` and `.mcp.json` from the Forge (frontmatter kept byte-for-byte). Each MCP server is written exactly as the Forge holds it, undeclared keys included, in its own key order — in a schema 4 Forge with the params its ingredient declares rendered into its string values (*Server params*). When a written MCP ingredient declares `authEnv` or a written hook declares `registration`, sync also writes `.claude/settings.craftar.example.json` — `env` with each declared name and an empty value, `hooks` with each registration to copy — for the developer to copy into their own, untracked `.claude/settings.json`; a hand-maintained `.claude/settings.example.json` is never touched; `kiro` and `agents-md` write no counterpart. Existing files keep their line endings and BOM; new files are LF without a BOM. Steering is Kiro-only (its `targets` default to `[kiro]`); one aimed at `claude-code` explicitly (`targets: "*"` or a list naming it) is skipped with a warning.

**kiro** — reproduces, then extends, the hand-written `sync-steering.ps1` script it replaces:
steering = `inclusion` frontmatter + `GENERATED` banner + rule body, with `.claude/rules/` rewritten to `.kiro/steering/` — except a reference to a rule kiro does not write, which follows that rule: kept as `.claude/rules/<x>.md` when `claude-code` writes it, `AGENTS.md (rule: <x>)` when only `AGENTS.md` holds it, otherwise `<x> (rule not in this workspace)` with a warning; an unknown name is still rewritten and is reported. A reference inside a link's text follows the same rules (in a link kept for `claude-code`, only those references move), and a link whose target reads "rule not in this workspace" and whose text is exactly its own path becomes `<x> (rule not in this workspace)` (backticks kept); an unknown name keeps its link. Files are UTF-8 without BOM, CRLF. The same applies to agent prompts and descriptions, command bodies and descriptions, and skill text files; a `steering` ingredient is emitted as written. On top of what the script did, it also generates `.kiro/agents/*.json` (tools mapped to Kiro names, `resources` bound to the agent's stack rule + `repo-discovery`, or `**/*.md` for generic agents), `.kiro/steering/commands/*.md`, `.kiro/skills/*/SKILL.md` and `.kiro/settings/mcp.json`. `.kiro/settings/mcp.json` receives each MCP server exactly as the Forge holds it (in a schema 4 Forge, as `.mcp.json` gets it: declared params rendered), in its own key order — including keys Kiro may not use (`type` always went through). The banner text is a parameter (`kiro.banner`) so existing workspaces can adopt without a rewrite. Scripts and hooks have no Kiro equivalent: they are skipped with a warning.

**agents-md** — one `AGENTS.md` with the always-on rules concatenated and the scoped rules after them — each listed at the file a target of the workspace writes for it (`.claude/rules/<name>.md` when `claude-code` writes it, else `.kiro/steering/<name>.md` when `kiro` does), or, when no target writes it, embedded in full under a `> Scoped rule — <scope>` line, for tools that read the open standard (Codex, Cursor, Warp, Copilot, Kimi…). A `.claude/rules/<x>.md` reference inside a body follows the rule it names: it is kept when `claude-code` writes that rule, becomes `.kiro/steering/<x>.md` when only `kiro` writes that file (from the rule or from a `steering` ingredient of that name), becomes `AGENTS.md (rule: <x>)` when the rule's text is in this file, and otherwise becomes `<x> (rule not in this workspace)` with a warning (an unknown name is left as written when `claude-code` is a target); a reference inside a link's text is resolved the same way, and a link whose target reads "rule not in this workspace" and whose text is exactly its own path becomes `<x> (rule not in this workspace)` (backticks kept); without `claude-code`, the warning also names references to other `.claude/` files, which are left as written. Every other ingredient type aimed at `agents-md` — including through the default `targets: "*"` — has no `AGENTS.md` equivalent: it is skipped with a warning — one line per type, naming every skipped ingredient. The file keeps the line endings and BOM of the one it replaces; a new one is LF without a BOM. **A size budget, `agents-md.maxBytes`** (default 32768 — Codex's `project_doc_max_bytes`; `0` turns it off), set in one of the layers that give params: a recipe's `params` (its `default` counts as set), the profile's `params`, or `overrides.params` in `craftar.yaml` or `craftar.local.yaml`; a value that is not a whole number of bytes is a warning, and the default applies. The size is the planned `AGENTS.md` in bytes; each rule body the file holds — always-on, and a scoped one embedded because no target writes it — is counted as its UTF-8 bytes after reference resolution and the trailing-newline trim. Over the budget every plan warns, naming at most 5 rules by name and bytes, never their content: `AGENTS.md is N bytes, over the default budget of 32768 (agents-md.maxBytes) — largest rules: a (n bytes), b (scoped, n bytes)`, or, when the budget is set, `… over the budget of M set by agents-md.maxBytes; sync --check fails — …`. Only a budget that is set fails anything: `sync --check`, `status` (and `status --json`, whose keys do not change — the reason is that warning) and `diff --exit-code` with no `[path]` exit 1 and print `error: AGENTS.md is N bytes, over the budget of M set by agents-md.maxBytes` with its fix; a writing `sync` still writes — so it never turns a `craftar workspaces` row into `error` (the table lists the warning under the workspace's path), `forge impact` does not show it, and the `next sync:` line does not count it (`add recipe`, `remove recipe` and `init --no-sync` still print the warning beside it). `doctor` reports it once, as `agents-md-size`.

**One home for the always-on rules, `agents-md.primary`** (a Forge at `schema: 5`). With `claude-code`, `kiro` and `agents-md` all targets, an always-on rule with the default `targets` is written three times — `.claude/rules/<x>.md`, `.kiro/steering/<x>.md` and its section of `AGENTS.md` — and Claude Code and Kiro each load two of them. Set the param `agents-md.primary: true` (a recipe default, the profile's `params` or `overrides.params`; a YAML boolean) in a Forge that declares `schema: 5` and a workspace whose targets include `agents-md`, and such a rule is written to `AGENTS.md` alone:
- **Who follows it:** a rule with `inclusion: always` whose `targets` is the default (`"*"`, written or omitted). A rule with a `targets` list keeps it — list `targets: [claude-code, agents-md]` to keep a rule in `.claude/rules/` too. Scoped rules, `steering` and every other type are untouched. The files the mode stops writing become orphans: `sync` removes them (its line reads `orphan: written to AGENTS.md only (agents-md.primary)`, and `diff`'s header `(forge: written to AGENTS.md only — sync removes it)`), and a hand-edited one is kept as an `orphan-drift` until `drift discard` or a delete.
- **References follow the rule:** in the `.claude/` files the `claude-code` emitter writes — a scoped rule's body, an agent's and a command's body and its `frontmatterRaw` (else its `description`), a skill's `.md` files — a `.claude/rules/<x>.md` reference is resolved as in `AGENTS.md`: `AGENTS.md (rule: <x>)` for a rule held there (a link loses its fragment), `.kiro/steering/<x>.md` for a rule only `kiro` writes. The `kiro` files reword such a reference to `AGENTS.md (rule: <x>)` too. Scripts, hooks and files copied as bytes are never rewritten: a reference there is warned with its file and line (`claude-code: … left as written in files craftar copies: .claude/scripts/lint.sh:2 (style)`), never with the line.
- **Kiro `resources`:** a generated list names only the steering files the plan writes, and never `file://AGENTS.md` (a custom agent inherits `AGENTS.md` — measured with kiro-cli 2.29.1). A hand-written `file://` entry with no glob under `.kiro/steering/`, `.claude/rules/` or naming `AGENTS.md` is checked: one the plan does not write and the disk lacks fails `sync --check`, `status` and `diff --exit-code` (a writing `sync` still writes); one only on disk is a warning. Measured with kiro-cli 2.29.1: a missing entry is no error to Kiro, and a `manual` steering file is not loaded through `resources` — neither by the glob `file://.kiro/steering/**/*.md` nor named alone.
- **`CLAUDE.md`:** Claude Code (2.1.277 or later) reads `AGENTS.md` only when no `CLAUDE.md` — at the root, in `.claude/`, or `CLAUDE.local.md` — is in the way, unless one imports it: a line `@AGENTS.md` (or `@./AGENTS.md`) in the root's `CLAUDE.md`, or `@../AGENTS.md` in `.claude/CLAUDE.md` (an import is relative to the file that holds it — measured with Claude Code 2.1.310). craftar never writes a `CLAUDE.md`; when the root holds one that blocks, every plan warns, naming the file and never a line of it. A Claude Code before 2.1.277 reads only `CLAUDE.md` and `.claude/rules/`, and loses the always-on rules without a word from craftar.
- `doctor` gains `agents-md-primary` (a blocking `CLAUDE.md` at the root, or one in a directory above the workspace — never above `warn`) and `kiro-resources` (`error` for an unplanned entry, `warn` for one on disk only), both only under the mode. Over the `AGENTS.md` budget, the warning adds `these rules are in no other file`. `drift promote` refuses a file the mode reworded (`drift show`: `reworded by agents-md.primary`), and `import` into a Forge that sets the mode compares each base as the mode writes it.
- Below `schema: 5` the key is not read (set to `true` it warns, and the mode is off); a value that is not a boolean, or the mode with no `agents-md` target, warns and leaves it off. **A workspace that does not set the key sees no change at all.** The key is reserved: `forge unify` never extracts into it and `import` never infers it.

**The rules index** (`schema: 7`). Each target writes the list with the references it writes for `.claude/rules/<x>.md` in a body: the `.claude/` and `AGENTS.md` lists name a rule `.claude/rules/<x>.md` when `claude-code` writes it, `.kiro/steering/<x>.md` when only `kiro` does and `AGENTS.md (rule: <x>)` when only `AGENTS.md` holds it; the `.kiro/` list names it `.kiro/steering/<x>.md` when `kiro` writes it (or a steering ingredient of that name), `.claude/rules/<x>.md` when only `claude-code` does and `AGENTS.md (rule: <x>)` when only `AGENTS.md` holds it. A path is in backticks; `AGENTS.md (rule: <x>)` is not. A rule no target of the workspace writes is left out, with no warning — so in a workspace without `agents-md` a rule aimed at `agents-md` alone is not listed. Under `agents-md.primary` an always-on rule with the default `targets` is listed as `AGENTS.md (rule: <x>)` in the other two lists. The `.claude/` and `AGENTS.md` lists are LF, the `.kiro/` list CRLF, as the rest of each file. `craftar explain <path>` names an indexed file's list (`index       craftar.rules.index (<n> rules)`), except for `AGENTS.md`, which is not one ingredient, and `drift promote` refuses a hand edit of one (D21).

Conversion of hooks/subagents to other tools is out of scope here: the plan is to delegate that to [rulesync](https://github.com/dyoshikawa/rulesync) rather than reimplement it.

## MCP servers on Windows and Linux

`.mcp.json` and `.kiro/settings/mcp.json` are committed, and one file serves every machine. Write an `npx` server in
the **portable form** — the program as `command`, the rest as `args`:

```yaml
# ingredients/mcp/example/ingredient.yaml
type: mcp
name: example
server:
  command: npx
  args: ["-y", "@acme/example-mcp"]
```

Not `command: cmd` with `args: ["/c", "npx", …]`: that form was once required on native Windows, starts on Windows only
(`cmd` does not exist on Linux or macOS), and is no longer needed — a bare `npx` starts on native Windows in both tools
(measured below). Move every such server to the portable form in the Forge; the next `sync` writes `update` for the two
files in every workspace of that Forge. craftar never rewrites it for you: `craftar doctor` warns for each one
(`mcp-launcher`) and `craftar import` warns when it reads one, keeping it as written. `command: "cmd /c npx"` as one
string starts in neither tool.

What was measured, by running each tool (stdio servers; Claude Code read from a project `.mcp.json`, Kiro CLI from the
workspace `.kiro/settings/mcp.json`):

| | Claude Code | Kiro CLI |
|---|---|---|
| `command: npx`, `args: ["-y", <package>]`, on native Windows | starts | starts |
| `command: cmd`, `args: ["/c", "npx", …]`, on native Windows | starts | starts |
| `command: "cmd /c npx"` (one string), on native Windows | fails | fails |
| `${VAR}` / `${VAR:-default}` in `command` | expanded | expanded |
| `${VAR}` / `${VAR:-default}` in `args` | expanded | **not expanded** — the text reaches the program as written |

Measured on Linux on 2026-10-23 (Claude Code 2.1.309, Kiro CLI 2.29.1) and on native Windows on 2026-10-24 (Claude Code
2.1.310, Kiro CLI 2.33.1, Node 22); the `${VAR:-default}` cases agree on both, and plain `${VAR}` was run on Linux only. The Kiro IDE and macOS were not measured. Later
versions may differ. So a `${…}` default in `args` works for Claude Code and not for Kiro: keep variables out of `args`
of a server Kiro writes.

## Design rules learned from the previous generator

These come straight from workspaces that removed an earlier generator, and the code enforces them:

1. **Only files in `craftar.lock` are ever written or removed.** A file that exists but was never generated is a *collision*: reported, never touched. A managed file that was hand-edited is *drift*: reported, never overwritten unless `--overwrite-drift`.
2. **Hashes are EOL- and BOM-normalized.** A CRLF checkout on Windows does not read as a hand edit. (`sha256` over LF/no-BOM text.)
3. **Orphans are removed.** When an ingredient leaves a recipe, its generated files disappear in every target — no stale steering loading into Kiro sessions.
4. **No hand-kept mirrors.** Kiro agents, commands and skills are generated from the same ingredients as their Claude counterparts.
5. **Reuse, don't clobber.** Importing a second workspace into the same Forge reuses identical ingredients and creates explicit `--<profile>` variants for the ones that differ, listing them so a human unifies or parameterizes.

## Local services

A workspace's local stack — a queue emulator, a cache — can be an ingredient. A **`service`** ingredient is a Docker Compose fragment plus the files it mounts:

```yaml
# ingredients/services/echo/ingredient.yaml
name: echo
type: service
files: [init/setup.sh]        # every other file written next to the fragment
executable: [init/setup.sh]   # a subset of files, written with mode 0755 (POSIX)
# binary: [init/logo.png]     # a subset of files copied as bytes — list it under files too
# compose: compose.yaml       # the fragment (this is the default)
params:
  greeting: { default: hello }
```

Every declared path — `compose` and each entry of `files`, `executable`, `binary` — is relative to the ingredient directory, with only letters, digits and `. _ @ + -` in each segment, no `.` or `..` segment (a leading `./` aside), and never `ingredient.yaml`. `files` lists neither the compose file nor a path twice — both, like `ingredient.yaml`, compared without regard to case, so `Init.sh` beside `init.sh` is refused. A file may be both `binary` and `executable`.

```yaml
# ingredients/services/echo/compose.yaml — a complete Compose file; paths are relative to it
services:
  echo:
    image: example/echo:1
    ports: ["8080:80"]
    environment:
      GREETING: "{{greeting}}"            # a craftar parameter, filled by sync
      TOKEN: ${ACME_TOKEN:-local}         # Compose's own variable, left for Compose
    volumes:
      - ./init:/init:ro
      - ${CRAFTAR_WORKSPACE}/projects:/src:ro
```

A recipe lists it like any ingredient (`service/echo`). `craftar sync` then writes, and records in `craftar.lock` under the owner `services`:

| Path | Content |
|---|---|
| `.craftar/services/<name>/<compose>` and each of its `files` | the fragment and its files, with sections expanded and `{{param}}` substituted — always written **LF without a BOM**, whatever the Forge holds (an init script with CRLF does not run in a Linux container). A file listed in `binary` is copied as bytes. |
| `.craftar/compose.yaml` | the stack: a Compose `include` of every fragment, in resolution order |
| `.craftar/.gitattributes` | `* -text`, so git never converts those line endings |

They are generated files like any other: `status`, `diff`, `sync --check` and `--overwrite-drift` treat them the same, and removing the last service from the recipes makes the next `sync` delete them. `sync` never runs Docker.

**The plan fails** when a fragment is not a YAML mapping, declares no service, declares a top-level `name` (the project name is craftar's) or `include` (every file of the stack is in the lock) — also when they arrive through a YAML merge key (`<<`): a fragment is checked as Compose reads it; when a service's `extends` names a `file` (it may extend a service of the same fragment), or when two fragments declare the same key under `services`, `volumes`, `networks`, `configs` or `secrets` — Compose would keep one silently. A file not listed in `binary` must be UTF-8 text. **It warns** when two fragments publish the same literal host port, and when a rendered file holds a secret-like value (the kind and the line, never the value): keep values out of the Forge and use `${NAME}`.

**Running it.** `craftar services up` runs `docker compose up -d` on the stack, `services down` stops it and `services status` shows it (see *Commands*). They need Docker with its Compose plugin, found on `PATH` by the lookup that finds `dotnet` and `git` (see *Project templates*); `up` needs Compose **2.20.0 or later** (the first with `include`), while `down` and `status` work on an older one. `sync` needs no Docker. `up` reads the lock, not the Forge: it comes up on what the last `sync` wrote, and refuses a file that is missing or edited rather than run something the lock does not record. Nothing runs Docker implicitly — not `sync`, not `init`, and `doctor` — the command, or the `doctor` tool of `craftar mcp` — only asks for the version. craftar adds no policy over what a fragment declares: a service runs with your Docker rights, as the hooks and scripts of a Forge run with yours.

- **The project** is `craftar-<slug>-<hash>`: the workspace directory's name, lowercased, every character outside `a-z 0-9 _ -` replaced by `-`, cut at 40, then the first 8 hex digits of the SHA-256 of the workspace's real path. It is computed, never written, so the files under `.craftar/` are the same on every machine and two checkouts are two projects. `services status` prints it. Moving a workspace changes it: stop the old one with `docker compose -p <old name> down`. A name that leaves nothing but dashes gives `craftar--<hash>`.
- **`${CRAFTAR_WORKSPACE}`** is set by `craftar services` to the workspace's real path, so a fragment can mount a repository of the workspace.
- **`.env`** at the workspace root is passed to Compose (`--env-file`) by `up`, and by `down` when it reads the stack, when it exists. craftar never reads its values; `craftar doctor`'s `services-env` reads only its key names, and warns for each `${NAME}` a fragment uses with no default (`${NAME}`, `${NAME?…}`, `${NAME:?…}`) that is set neither in the environment nor there. Only the braced form is read. A key is read as `NAME=` at the start of a line. `CRAFTAR_WORKSPACE` is never reported.
- **Plain Compose** works too, for `logs`, `exec` and the rest: `CRAFTAR_WORKSPACE="$(pwd -P)" docker compose -p <project> -f .craftar/compose.yaml [--env-file .env] logs -f`.
- **Sections in a fragment.** A section marker is a whole line, so a Forge fragment holding one is not valid YAML until `sync` renders it, and `docker compose config` cannot be run on the Forge copy; `{{param}}` has no such cost.
- **Older craftar.** A Forge with a service ingredient needs this version in every workspace that reads it, whether or not the workspace uses the service — see *Upgrading*.

## Remote Forge

`forge:` may be a git URL — `https://…`, `ssh://…`, `file://…`, or the SCP-like `git@host:org/forge.git` (any SSH user) — with an optional `ref`: a branch (followed: its tip at each fetch), a tag or a full 40-hex SHA (fixed); `refs/heads/<x>` / `refs/tags/<x>` when a name is both; no `ref` follows the remote's default branch. Abbreviated SHAs are refused. A `ref` next to a path `forge:` is ignored, with a warning.

- **The cache.** Each machine keeps one copy per URL in `$CRAFTAR_HOME/forges/` (`~/.craftar` by default): a bare repository and one tree per resolved commit, never written by Craftar, shared by every workspace on the machine. Each tree holds the commit's bytes on every platform: the host's `core.autocrlf`, `core.eol` and global attributes file do not apply to it; the Forge's own `.gitattributes` does. Trees unused for 14 days are removed after a fetch. `craftar cache prune` removes whole entries nothing uses and old trees on demand (see *Commands*). The cache and the workspace registry (below) are the two places, both under `$CRAFTAR_HOME`, where Craftar writes outside a workspace and a Forge on its own.
- **The network.** `sync` (with `--check` and `--dry-run`) and `diff --exit-code` fetch first and exit 1 when they cannot; `status`, `diff`, `explain`, `ls`, `recipes`, `ingredients`, `add recipe`, `remove recipe`, `forge variants` and `forge diff` fall back to the cached copy with a warning; `--offline` uses the cached copy on purpose; with no cached copy every one of them exits 1. `targets` never fetches: it reads the cached copy, and without one prints the matrix unmarked, with a warning. A full SHA already cached is not fetched again.
- **Authentication belongs to git** (credential helper, SSH agent). A URL holding credentials (`https://user:token@…`, a password in any scheme) is refused in `craftar.yaml` and `craftar.local.yaml`, naming the file and never the value. In CI, configure git (e.g. a credential helper or an SSH deploy key), never a token in `forge:`; without a terminal, git does not prompt.
- **Writing into the Forge** stays local: `import`, `forge unify` and `forge promote` need a clone passed as `--forge <dir>`; Craftar never pushes. After importing into the clone, push it for `sync` to see the import.
- **`craftar.local.yaml`** may override `forge:` (a local clone while you work on the Forge); every planning command then warns not to commit `craftar.lock` or the generated files.

## Workspace registry

A writing `sync` records the workspace in `$CRAFTAR_HOME/registry.json` (`~/.craftar` by default): its real path, profile, the Forge it used and where that Forge lives, the resolved recipes and targets, and when `sync` last ran there. It is an index, not the memory — `craftar.lock` stays that, and nothing in a workspace changes because of it. `craftar workspaces` prints it as a table with every status computed on the spot — `up to date`, `outdated`, `drift`, `no lock`, `missing` or `error` — read without the network (a remote Forge from the cache; `--fetch` fetches first); `forget` and `prune` remove entries, and a workspace that is gone stays listed as `missing` until you prune it.

- **`CRAFTAR_NO_REGISTRY`** — read the name as "no registry", the way `NO_COLOR` means "no colour". Set to any non-empty value, it turns the registry off: `sync` neither reads nor writes it, and `craftar workspaces` and `craftar ui` exit 1. An empty value counts as unset. Set it on CI runners and throwaway checkouts, whose directories would only pile up as `missing`.
- **A registry that cannot be written** (an unwritable `$CRAFTAR_HOME`, a busy lock after 60 s, a file this craftar cannot read) leaves `sync`'s files, lock and exit code as they would be, and adds one warning. Craftar never overwrites a registry it cannot read: repair or remove it yourself.
- The registry is per machine: paths are native and absolute, and SSH and HTTPS spellings of one remote are two Forges in it, as they are two cache entries.
- **`craftar init` reads it for the Forge it offers** when it asks: the Forge of the most recent `sync` on this machine, skipping a directory that is gone. The questions never write it — the first `sync` registers the new workspace as any `sync` does. With `CRAFTAR_NO_REGISTRY` set, or a registry it cannot read, no Forge is offered and the question is asked without a default.
- **The registry also tells a Forge its workspaces**: `forge impact`, `forge unify` and `forge promote` read it (never write it); a workspace synced on CI, another machine or under `CRAFTAR_NO_REGISTRY` is not known to them, which is why `--prune-recipes` says so.

## Project templates

`craftar templates list` shows what the profile declares; `craftar templates install` runs the installs. **Nothing installs implicitly** — not `sync`, not `init`, not `doctor`.

A profile can list templates to install:

```yaml
# profiles/acme/profile.yaml
templates:
  - kind: dotnet-new
    source: https://pkgs.example.com/acme/nuget/v3/index.json
    packages:
      - Acme.Templates.Api
      - Acme.Templates.Front::2.1.0
```

A `kind` is a lowercase name (`dotnet-new`); a package is a NuGet ID, optionally with a version (`<id>::<version>`). A `source` is an `https://` URL with a host, in printable ASCII, and no user or password. There is no workspace layer: `craftar.yaml` and `craftar.local.yaml` cannot add or remove a template.

- **The store is the user's** — one per machine user, shared by every workspace; the last install of a package ID wins. Remove one with `dotnet new uninstall <package>`.
- **Feeds are additive** — a declared `source` is added to the feeds `dotnet` already uses, so an ID nobody reserved on a public feed can be served from there. Pin it with the team's own `NuGet.Config` at the workspace root (craftar looks there only, and generates none). `install` and `doctor` — the command, or the `doctor` tool of `craftar mcp` — warn when an entry declares a `source` and the root has no `NuGet.Config`.
- **Private feeds** — authentication is NuGet's (`NuGet.Config`, a credential provider, `--interactive`); craftar holds no token, and a `source` carrying a user or a password is refused and never printed. A `source` is printed as written by `list`, `--dry-run` and `install`: craftar refuses a user or a password in it, not a token in its path or query — keep those out of the profile.
- **`dotnet` comes from `PATH`** — craftar looks for it itself, in the absolute entries of `PATH` only (on Windows, a `dotnet.exe` or `dotnet.com` in an entry with a drive or a UNC host), and never in the workspace root unless `PATH` names it: a `dotnet` committed in a repository is not run by `install` or by `doctor`'s probe (the command's, or that of the `doctor` tool of `craftar mcp`), all of which run there. An empty or relative entry, an unset `PATH` and a `.cmd` / `.bat` shim are not used, and neither is a `node_modules/.bin` of the directory craftar is started in or of a directory above it — the entries `npx` and `npm` put first. The same lookup finds `git` and `docker`.
- **Unknown kind** — an entry of a kind this craftar cannot install (`npm-create`, `nx`) is listed, skipped and warned; `install` then exits 1 (`--dry-run` still exits 0).

## Craftar inside the AI coder

An AI coder working in a generated workspace does not know the files are generated. `craftar mcp` tells it: registered as an MCP server, it lets the agent ask what is pending, why a file exists and what the Forge offers — and say "run `craftar sync`" instead of editing a generated file.

**In Claude Code, the plugin.** Install `craftar` first (`npm install -g craftar`, version 0.40.1 or later: an older one connects, but its `doctor` tool can run a repository's code), then:

```text
/plugin marketplace add llima/craftar-cli
/plugin install craftar@craftar
```

The plugin holds a `/craftar` skill and starts the `craftar` found on `PATH` in every project it is enabled for, with the seven reading tools only: never `--allow-writes`, never `--fetch`. In a project with no `craftar.yaml`, or in a subfolder of a workspace, the server reads as failed: it refuses to start, no tool is offered and nothing is written. See [its README](plugins/craftar/README.md) for what it reaches before you enable it everywhere.

Register it by hand, in the AI coder's own MCP configuration — a file `sync` does not write (the user's own, not a generated `.mcp.json` or `.kiro/settings/mcp.json`):

```json
{ "mcpServers": { "craftar": { "command": "craftar", "args": ["mcp"] } } }
```

or for a whole team, as an ordinary `mcp` ingredient in the Forge, which `sync` writes to `.mcp.json` and `.kiro/settings/mcp.json` like any other server:

```yaml
# ingredients/mcp/craftar/ingredient.yaml
type: mcp
name: craftar
server:
  command: craftar
  args: [mcp]
```

The server answers for the directory it is started in; a client that starts its servers elsewhere needs `args: [mcp, --workspace, <dir>]`. The server also sees only the environment the client starts it with: `git`, `dotnet` and `docker` are looked for in the absolute entries of that `PATH` (a `node_modules/.bin` of the directory the server is started in, or of one above it, aside — see *to 0.28.2*), and the variables `doctor` checks are read there — so a client that starts its servers with a reduced `PATH` gets `git not found` from `doctor` (its `dotnet` and `docker` checks warn too, when the workspace uses them and its Forge loads), no commit for a Forge that is a directory and, when the Forge is a git URL, an error from `status`, `diff`, `explain`, `recipes` and `ingredients` — `targets` then answers the matrix unmarked, with a warning, and `doctor` reports `git` as an `error` and, of the workspace's checks, runs only `lock`.

**Letting it write.** Started with `--allow-writes` (`args: [mcp, --allow-writes]`), the server also lists `sync`, `add_recipe` and `remove_recipe`. The flag grants nothing by itself: each writing call reads this machine's registry and acts only when a person typed `craftar mcp allow-writes` in this workspace, in a terminal, for the Forge, ref and profile the server is pinned to — so a Forge that puts `--allow-writes` in its `craftar` ingredient makes the tools appear in every workspace that syncs it, and write in none until someone there consents. `craftar mcp revoke-writes` takes the consent back. The consent refuses to be recorded outside a terminal; the shell tools of Claude Code and Kiro run without one (measured on 2026-10-23: neither gives a program a terminal on stdin or stdout), so an agent cannot grant it through them — an agent that drives a real terminal could, and could type `craftar sync` there as well. `sync` never overwrites or removes a hand edit: a `drift`, an `orphan-drift` and a `collision` are skipped and listed, and a person resolves them with `craftar drift discard` or `craftar drift promote`. Writes are not locked against a `craftar sync` run at the same moment in a terminal; each re-reads the disk just before it writes.

**What the results hold.** A tool result goes wherever the AI coder sends its context, and the tools return the commands' data with three things left out: `doctor`'s checks about the rest of the machine (`$CRAFTAR_HOME`, the registry, the Forge cache), the on-disk content of a hand-edited MCP configuration file, and — from `diff` without a path — the bodies (it lists counts). Nothing else is filtered. So a result can hold: the content of a generated file with its hand edits, or of a file craftar never wrote that sits where it would write one (`diff` with a path, on a `drift` or a `collision`) — a hand-edited service file under `.craftar/` included; values a profile or `overrides.params` put into a generated file; the Forge's path or URL as `craftar.yaml` names it; the absolute path of the workspace and of a path Forge, the Docker Compose and .NET SDK versions found on this machine and the names of the variables a service fragment expects — names, never values (`doctor`); and **the names of every profile of the Forge and the workspace an ingredient was imported from** — the profiles beside each recipe in `recipes`, the origin in `explain`. In a Forge shared across clients those names can be client names — register the server only where that is acceptable.

## Roadmap (from the functional spec)

Phase 0 — foundations (done): schema, import, sync/status/diff/explain, claude-code + kiro + agents-md targets, lock, drift, orphans; `forge variants`, `forge diff` and `forge unify` (`take: param`, `take: section`); sections.

Phase 1 — client profile (in progress). Shipped: the read-only catalogue (`recipes`, `ingredients`, `targets` with the capability matrix); remote Forge (git URL + `ref`, a per-machine cache, the schema 2 lock) and `craftar cache prune`; the workspace registry and `craftar workspaces`; `craftar add recipe` / `remove recipe`; `craftar init` with flags; `craftar doctor`; `craftar forge impact`, `forge unify --prune-recipes` and `forge promote`; an interactive `craftar init` (choose the Forge and the profile); `authEnv` on MCP ingredients (the environment variables a server needs, by name, and the generated `.claude/settings.craftar.example.json`); `craftar drift show` / `drift discard` / `drift promote` (list the files edited by hand, discard an edit, or carry one into the Forge as a profile value or a variant); a sync refused when a declared parameter has no value; `craftar import --report` (a Markdown report of an import, as paths and line counts) and `import --prefer-kiro` (a rule's source taken from its Kiro steering file); a profile's `integrations` block (PM tool and IDP as recipes selected by the profile); `{{param}}` inside an MCP server; `craftar mcp` (a read-only MCP server: seven reading tools for an AI coder, over stdin and stdout); `craftar ui` (a local, read-only dashboard of the registered workspaces, on `127.0.0.1` only); cloning a profile's repositories (`init --clone`, `craftar repos`); a new profile from `craftar init` (`--new-profile`, `--like`); writing tools for `craftar mcp` (`--allow-writes`: `sync`, `add_recipe`, `remove_recipe`, behind a consent typed per workspace); writing actions in `craftar ui` (`--allow-writes`: Sync and Discard edit, confirmed in the page); the Claude Code plugin of `craftar mcp` (`plugins/craftar/`: a `/craftar` skill and the reading tools).

Phase 2 — environment (in progress). Shipped: local services (`service` ingredients, `.craftar/`, `craftar services up | down | status`); `craftar templates list | install` (`dotnet new` project templates declared in a profile).

Later: rulesync bridge for Codex/Kimi/Cursor specifics; `craftar docs validate`; GitHub Action and Azure Pipelines task around `sync --check`; the Agent Plugin packaging of `craftar mcp`.

## Upgrading

### to 0.44.0

- **`craftar doctor` gains `git-hooks`**, present only when a marked hook is installed; a `warn` when no `craftar` is on `PATH`, since the hook then checks nothing, so `doctor --strict` exits 1 there. Nothing else changes for a workspace with no hook.

### to 0.43.0

- **A symbolic link no longer carries craftar out of the tree it works on.** A Forge file the plan reads through a link that leaves the Forge, or that leads into its `.git`, now fails the plan: replace it with a file. A path of a workspace that leaves it through a link now refuses `sync` and is reported by `status`, `diff --exit-code`, `sync --check` and `doctor` (`workspace-links`, an `error`, so plain `doctor` exits 1): replace the link with a directory or a file inside the workspace. `craftar.lock`, and `craftar.yaml` when craftar would write it, are held to the same rule. There is no flag, and no Forge `schema:` gate.
- **A link that stays inside either tree works as before**, but for a link into the Forge's `.git` or the workspace's `.git`, and a dangling link where craftar would write, which are refused. A dangling `ingredient.yaml` or `profile.yaml` fails the load where it was skipped.
- **`forge variants`, `forge diff`, `forge unify`, `forge promote` and `import` fail on a link out of the Forge in a directory they read**, emitted by a target or not, which `sync` does not refuse when nothing reads it. `forge promote` and `drift promote` no longer refuse an unread dangling link or file link out; a root `ingredients`, `recipes` or `profiles` link that leaves with files in it now fails the load, in these words.
- **`services status --json` can report a `pending[].reason` of `link`**, and `drift show` gives such a file `promotable: false`; `drift promote` refuses an ingredient holding one.
- **`import` rejects a file that leaves the workspace or leads into its `.git`, where it adopted it**, an exception to *Adopt, don't collide*; on a re-import it leaves the profile's recipes. It refuses the run on a source directory or `.mcp.json` that leaves, and refuses to write through a link out of the Forge, into its `.git` or leading nowhere.

### to 0.42.0

In a Forge with no manifest yet, a recipe that does not load refuses the import too, even one import does not write, and a profile that does not load now names its file.
- **A key a run already relied on renders at its current value.** Import no longer infers it again, so a line that was ambiguous only through it can now be reused.
- **Some sources 0.6.0 reused become variants.** A profile value is no longer set when it would move a Forge ingredient whose workspace copy was skipped or rejected for a secret, nor over a default an earlier ingredient of the run rendered with (0.6.0 set it; when another earlier ingredient rendered the key at a different default, that one changed at the next `sync`).

### to 0.6.0

- **Re-import is template-aware.** A workspace whose text an extracted base renders (through its defaults or the profile's `params`) is reused instead of becoming a variant, and a new client's values are inferred into its profile.
- **A second client no longer widens `base`.** A profile whose ingredients differ from a shared recipe gets its own `<recipe>--<profile>`. Profiles that already resolve a widened `base` keep it until their next re-import.
- **An existing profile, owned recipe and `craftar.yaml` are edited in place.** Their comments and every other field survive, but the lists import computes are set to this workspace's: an owned recipe's `ingredients`, the import-owned entries of the profile's `recipes` (`base`, `stack-*`, their `--<profile>` recipes and `<profile>-steering`) and `craftar.yaml`'s `forge`, `profile` and `targets`. A file that does not round-trip through the YAML writer is refused (reformat it and re-run). The `created` count no longer lists an existing profile.
- **A profile value can change on re-import.** When a workspace shows another value for a key its profile sets, the profile is updated and the report says `param <key>: <old> → <new>` — every workspace on that profile renders it at its next sync.
- **`import` now loads an existing Forge first**, and refuses one that does not load.

### to 0.5.0

- **A Forge edited by `forge unify` with `take: param` needs 0.5.0 everywhere.** The base's `ingredient.yaml` gains `params`, which `craftar` 0.4.0 and older refuse as an unknown key. Upgrade every workspace that syncs that Forge.
- **`import` is not template-aware yet.** Re-importing a workspace into a Forge whose base now holds `{{key}}` creates a new variant of it and rewrites the profile's `profile.yaml` without the extracted `params`. Avoid re-importing over an extracted base until 0.6.0.
- **`{{constructor}}`, `{{toString}}` and `{{__proto__}}` stay literal.** `substitute` used to resolve them to built-in JavaScript members; a body holding one now keeps it verbatim (and `status` warns that it has no value).

### to 0.3.0

- **Unknown `ingredient.yaml` keys are refused.** A Forge with a key the schema does not declare stops loading; the error names the file and every unknown key. Rename or remove the key and commit the Forge (`forge unify` refuses paths git does not hold), then re-run. MCP `server` keys are the exception: they pass through.
- **MCP files may show `update`.** `.mcp.json` and `.kiro/settings/mcp.json` now carry every key of a server as the Forge holds it (`headers`, `timeout`, `disabled`…) in its own key order. Workspaces whose servers have undeclared keys, or keys stored out of `command`/`args`/`url`/`env`/`type` order, see `update` on those files once; an unlocked `.mcp.json` that read `collision` because of undeclared keys or `type` first now adopts.
- **Saved `forge unify` plans may go stale.** Fingerprints now hash validated metadata, so a hand-written `ingredient.yaml` that omits defaulted fields fingerprints differently. `--plan` refuses a stale plan; re-run `--save-plan`.
- **`import` is stricter and reuses more.** An ingredient that would not load back (a non-string MCP `env` value, a name that is not slug-like) refuses the import, naming its source, and so does an existing Forge ingredient with an unknown key or a YAML syntax error (0.2.4 made a variant or an error naming no file). A re-import may now reuse an ingredient where it used to create a variant.

## Releases

Merging a pull request that bumps the version in `package.json`, `package-lock.json` and
`src/cli.ts` starts a release: when that merge's CI run is green, `.github/workflows/release.yml`
checks that the three files agree and that the version is not on npm yet, dry-runs the package,
and waits for a maintainer to approve the `npm` environment. After approval it publishes
`craftar@<version>` with npm trusted publishing and provenance — no npm token is stored in the
repository — and creates the `v<version>` tag and a GitHub Release. A merge that does not change
the version publishes nothing.
